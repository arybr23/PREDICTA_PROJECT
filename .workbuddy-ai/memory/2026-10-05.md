# 2026-10-05

## Closed the import → ML bridge (was the open gap from the upload investigation)

Root cause recap: `POST /sales/import` wrote only `ML/datasets/<id>.csv`; the
per-store `raw/` and `processed/` trees were reachable only from `append_daily_log`
(spawned by `POST /sales/entry`). So a successful upload left the store unable to
forecast, silently (import returned `status:"success"`).

Changes:
- **`ML/src/rebuild_store_history.py`** (new): reads the dataset and derives the
  40-col history + 25-col feature matrix in one pass. Accepts `--weather`
  (date → {weather,temperature} map), `--menu` (for `item_category`),
  `--skip-features`. Idempotent (rewrites history from scratch each run).
- **`BE/services/weather.js`**: added `fetchRange(location, from, to)` — one
  Open-Meteo request for the whole span (backfill). Verified reachable from the
  sandbox.
- **`BE/services/python.js`**: added `rebuildStoreHistory()`, `datasetPath()`,
  `datasetSpan()` (min/max date in the dataset, sizes the weather fetch).
- **`BE/routes/sales.js`**: `POST /sales/import` now calls `runPostImportBridge`
  after a successful import — backfills weather → rebuilds history → trains if
  `days > MIN_DAYS_TO_TRAIN`. Weather-fetch failure is swallowed. Added a
  standalone **`POST /api/sales/rebuild`** for already-imported stores (reads span
  via `datasetSpan`, backfills, rebuilds, trains). Import response now includes a
  `bridge` summary (`history_days`, `weather_backfilled`, `trained`, …).

Verified end-to-end against STR-4418 (already-imported, 720 days / 18k rows):
- `datasetSpan` → 2024-09-27 → 2026-09-16; `fetchRange` returned 720 real days.
- history now has `temperature` on 18000/18000 rows (was 0) and `item_category`
  filled; `feature_matrix.csv` = 18000 × 25; `active_model.model` trained
  (MAE 38.82 → 18.38).
- `predict.py` → 25 items predicted, 1960 total units. The store can now forecast.

Note: `getForecast` returns per-item predictions under `menu_breakdown` /
`total_items_predicted`, NOT under a `forecast` array key.

Mongo `find`/`findOne` hung this session (DB under load?), so verification ran the
exact BE modules in-process instead of through the HTTP layer. `node --check`
passed on both edited BE files.
