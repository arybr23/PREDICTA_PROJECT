# Session 6 — weather data source research

Asked whether an open API could replace manual weather entry. Researched and
**actually tested** Open-Meteo against Surakarta (-7.5755, 110.8243) — the
location of `STR-4418`.

## Recommendation: Open-Meteo
`https://archive-api.open-meteo.com/v1/archive` — free, **no API key, no
registration**. Verified HTTP 200 with real data. Back to 1940 (ERA5),
`timezone=Asia/Jakarta`, daily params:
`weather_code, temperature_2m_max, temperature_2m_min, precipitation_sum,
precipitation_hours, rain_sum, shortfall...`.

Free tier limits (from the pricing page): 600/min, 5,000/hour, 10,000/day,
300,000/month. **Free tier is non-commercial only**; a commercial licence needs
the Professional plan. Data is CC BY 4.0 → attribution required.

Call counting: >10 variables or >2 weeks of one location counts as multiple
calls (~2 weeks = 1 call). A 2-year backfill ≈ 52 calls, trivial.

## ⚠️ THE FINDING: the synthetic weather distribution is wrong
Measured 733 days of real Surakarta weather and compared it to
`WEATHER_TYPES` in `generate_mock_data.py`:

| label | synthetic | actual | delta |
| --- | --- | --- | --- |
| cerah | 30% | **1.1%** | −28.9pp |
| berawan | 25% | 9.0% | −16.0pp |
| hujan_ringan | 25% | 31.8% | +6.8pp |
| hujan_deras | 15% | **37.1%** | +22.1pp |
| panas_extreme | 5% | 21.0% | +16.0pp |

Reality check (mapping-independent): mean tmax 31.5 °C, range 26.4–37.2 °C,
154/733 days ≥ 33 °C, only 18.1% of days completely dry.

Consequences:
- `predict.py`'s `DEFAULT_WEATHER = "cerah"` conditions every forecast on a
  state that occurs ~1% of the time in Surakarta.
- The model learned weather multipliers at frequencies that do not occur in the
  field, so the `weather` feature contributes at the wrong rate.
- This is a concrete, quantified answer to the judges' "does your synthetic data
  reflect reality?" question (see Session 4, Question 1).

Caveat: the code→label mapping is a judgement call (I used tmax ≥ 33 → 
panas_extreme first, then WMO code bands, then a precipitation fallback). The
robust part is the direction and magnitude, not the exact percentages.

## ⚠️ CORRECTION (same session): the percentages above are rule-dependent
The table above used the **daily** `weather_code`, which Open-Meteo defines as
the **most severe** hourly code of the day, not the typical one. Verified on
2026-09-30: 15 hours code 0 + 2 hours code 1 + 7 hours drizzle → the day reports
`55` (dense drizzle). One bad hour brands the whole day.

Re-measured the same 733 days using the **most common** hourly code instead:

| label | most-severe hour | most-common hour |
| --- | --- | --- |
| cerah | 1.1% | 13.0% |
| berawan | 9.0% | 51.4% |
| hujan_ringan | 31.8% | 14.6% |
| hujan_deras | **37.1%** | **0.0%** |
| panas_extreme | 21.0% | 21.0% |

**69.2% of days change label** depending on which rule you pick. So the earlier
"hujan_deras 37.1% vs 15% synthetic" was largely an artifact of the most-severe
rule — do not quote it. With the modal rule `hujan_deras` is 0%, because heavy
rain is brief by definition and is therefore never the modal hour.

**Conclusion: do not derive the label from `weather_code` at all.** Neither
aggregation is defensible. Build the label from the honest aggregates —
`precipitation_sum` (a true daily sum) for the rain axis and
`temperature_2m_max` (a true daily max) for the heat axis — and use the code
only to split dry days into cerah vs berawan.

Deeper issue: the 5-label taxonomy assumes rain is occasional. Surakarta has
only 18.1% completely dry days, so "rain / no rain" is not a useful axis there;
intensity is.

## What the API actually returns per day (verified)
- `daily=` → exactly **1 value per variable per day**; `time` is one date.
- `hourly=` → exactly **24 values per variable per day**.
- Daily `temperature_2m_max/_min` = max/min of the 24 hourly readings.
- Daily `precipitation_sum` = sum of the 24 hourly readings.
- Daily `precipitation_hours` = count of hours with precipitation > 0.
- Daily `weather_code` = **max** (most severe) of the 24 hourly codes.
- `timezone` is **required** when using `daily=` — the aggregation window is the
  local day, so `timezone=Asia/Jakarta` is mandatory or days shift by 7 hours
  against the app's own `localDate()`.

## Blocker for integration
**`Stores` has no location field.** There is no lat/lon anywhere in the schema,
so per-store weather needs a `location { lat, lon }` (and ideally a
`timezone`) added first.

## Other sources surveyed
- **NASA POWER** — free, no key, daily from 1981/01/01 to near-real-time,
  0.5° grid, up to 20 params/request, `community=AG`. Good agro-climate
  alternative.
- **Meteostat** — free, API key via free registration, station-based + bulk
  dumps, 1940s onward.
- **Visual Crossing** — API key, free tier 1,000 records/day (commercial use
  allowed), then $0.0001/record, 40+ years.
- **BMKG** — Indonesian agency, open data, but the historical daily archive
  (`dataonline.bmkg.go.id`) needs an account and is station-based, not lat/lon.
- OpenWeatherMap / Tomorrow.io — history is behind paid plans.

Also noted: ERA5 has a ~5-day lag; recent days come from ECMWF IFS via
`best_match`, which is why yesterday's data was already available.

# Session 8 — what creates raw/ and processed/, and a bug found doing it

Asked what triggers the per-store `raw` and `processed` directories. Traced it,
and the trace exposed a defect that is now fixed.

## The trigger (one chain only)
`POST /api/sales/entry` → `python.appendDailyLog(payload, storeId)` →
`append_daily_log.py --store <id>`, which:
1. `bootstrap_history(raw_path)` — **creates `data/raw/stores/<id>/` + a
   header-only `historical_sales.csv`**.
2. `build_feature_matrix(output_path=…, label_map_path=…)` — **creates
   `data/processed/stores/<id>/` + `feature_matrix.csv` + `label_encoders.json`**.

`POST /sales/entry` then calls `incremental_train.py --store` (unless
`train:false`), whose `os.makedirs` **creates `models/stores/<id>/`**.

Nothing else creates them. `predict.py`, `benchmark.py` and
`incremental_train.py` only read. `--skip-features` suppresses step 2 but no
caller in the app passes it.

Note `bootstrap_history` runs **before** the payload rows are validated, so a
run that later fails at `upsert` still leaves a header-only history behind.

## 🐞 Bug found and fixed
`forecast.js`'s `NOT_READY` regex listed `"Historical sales data missing"` but
`predict.py` also fails with **`"Historical sales data is empty"`** when the file
exists with zero rows. The wording gap meant that state returned **503
"Forecast engine unavailable"** instead of a clean `200 {empty:true}`.

Reachable when a store has a model + encoders but an emptied history — e.g. the
CSV is reset after training, or a write is interrupted between training and the
CSV write. `hasStoreHistory()` is a pure existence check, so it lets the request
through to Python.

Fixed by matching the concept rather than the exact string: `Historical sales
data missing` → `Historical sales data`.

Verified: constructed header-only history + real encoders + a real model →
before the fix `503`, after the fix `200 {empty:true, reason:"model_not_ready"}`.

**Method note:** my first repro attempt did *not* reproduce, because
`resolve_model()` fails earlier with "No trained model", which the regex does
match. It took constructing the full state to reach the unguarded branch.
Test the specific branch, not the general suspicion.

## Also confirmed
A store's history CSV has **40 columns but only 18 are ever populated with
store data**; 6 (`holiday_name`, `active_events`, `base_demand`,
`gregorian_mult`, `hijri_mult`, `weather_demand_mult`) are generator artifacts
copied in with the header and are permanently empty, and 14 lag/rolling columns
stay empty on day 1.

# Session 11 — cashier menu list, search, and shared sold-out state

## What the user asked for

2. Add a **search bar** that filters as you type
3. **Move the stockout toggle into the menu area** (it was a separate panel)

## The sync bug, and why it existed
The Cashier read `store.stockouts` (persisted, via `GET /pos/menu`, written by
`PATCH /pos/item-status`). Data Entry's toggles read **local state seeded from
the staged sales flag** — a completely different thing. Two concepts wearing the
same label, so they could never agree.

Fix: `store.stockouts` is the single source of truth.
- `GET /catalog` now returns `stockout` (it did not before) — this was the
  missing half.
- `DataEntry.handleStockoutChange` now PATCHes `/pos/item-status` and updates
  optimistically with rollback, instead of only setting local state.
- `effectiveStockouts` falls back to `item.stockout` from the catalog, no longer
  to `stagedById`.

  inline per-row sold-out switch. `MenuGrid.jsx` and `StockoutFlag.jsx` deleted.

  can be tested.
- `FE/.../Cashier/Cashier.jsx` — uses MenuList; `pendingStockoutId` disables just
  the switch in flight.
- `FE/.../DataEntry/DataEntry.jsx` — stockout write-through.
- `BE/routes/index.js` — `/catalog` carries `stockout`.

## Markup note
The row's add-to-cart action and its sold-out switch are **siblings**, not nested

# Session 12 — diagnosing the empty raw/ and processed/ after an import

The user uploaded a file: `ML/datasets/STR-4418.csv` was written (578 KB,
18,000 rows, 720 days × 25 items, 2024-09-27 → 2026-09-16) but
`ML/data/raw/stores/`, `ML/data/processed/stores/` and `ML/models/stores/` were
all empty. This is exactly the gap flagged in Session 9.

## Root cause (not a failure — a missing bridge)
`import_sales.py` has **no code path** to either downstream directory. Proven by
call-graph grep:
- `bootstrap_history()` — 1 caller: `append_daily_log.py:171`
- `build_feature_matrix()` — 2 callers: `append_daily_log.py:197` (per store),
  `dataset_prep.py:194` (its `__main__`, global paths only)
- `import_sales.py` references only `DATASETS_DIR` and `write_dataset`

And by route-level grep:
- `POST /sales/import` calls `python.importSales` + `clearForecastCache`. Nothing
  else.
- `POST /sales/entry` calls `storeDataset.rowsForDate`, `storeDataset.upsertDailySales`,
  `python.appendDailyLog`, `python.trainIncremental`.

## Demonstrated
Ran both paths on a throwaway id `DEMO-TRACE`:
- after `import_sales.py`: `ML/datasets/DEMO-TRACE.csv` present; the three
  downstream dirs **did not exist**
- after `append_daily_log.py`: `raw/stores/DEMO-TRACE/historical_sales.csv` and
  `processed/stores/DEMO-TRACE/{feature_matrix.csv,label_encoders.json}` appeared

Cleanup done; the user's `STR-4418.csv` untouched.

## Why it is silent
The import returns `status: "success"` — it did exactly what it was written to
do. Nothing errors, so nothing surfaces. The 578 KB dataset looks like success.

## The fix, when they want it
Either have the import also build the history (bulk `append_daily_log` over the
imported days), or make `append_daily_log.py` accept a date range. The former is
simpler; the latter avoids re-parsing.
